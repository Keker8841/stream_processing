# Архитектура обработки

Один процессор `vq-service`. Внутри два слоя:
- `Engine` — чистое ядро правил: без ввода-вывода, без системных часов, без случайности;
- `ServiceApp` — слой Kafka: транзакции, снимок состояния, восстановление.

```
telemetry.v1 (1 партиция, ключ unit_uuid)
      │  группа vq-service, read_committed
      ▼
  vq-service ── Engine: состояние всей площадки в памяти
      │  одна транзакция = выходы пачки + снимок + офсеты входа
      ├──▶ queue.v1     ключ station_uuid, compacted
      ├──▶ decision.v1  ключ unit_uuid, заголовок decision-id
      └──▶ vq.state.v1  compacted, ключ state_key: снимок Engine + офсеты входа
```

## 1. Сколько процессоров и по какому критерию

Один. Критерий: всё, что должно измениться атомарно в ответ на одно входное сообщение, находится в одном процессоре.

Одно сообщение телеметрии меняет сразу:
- «сейчас» площадки;
- состояние машины;
- занятость станции;
- очереди всех станций: свежесть позиций и горизонт отсчитываются от общего «сейчас»;
- при пересечении 1500 м — решение, которое в том же сообщении переносит машину в очередь другой станции.

## 2. Ключ процессора и его состояние

Ключ — площадка. Весь `telemetry.v1` площадки — один упорядоченный поток, его обрабатывает один экземпляр.

Состояние — снимок `Engine`, около 10 КБ на 40 машин:

| Где | Что хранится |
|---|---|
| Площадка | «сейчас», то есть наибольший учтённый `ts` |
| Машина | последний учтённый `ts`, позиция, скорость, фаза (`к станции` / `к разгрузке`), применённая рекомендация, признак «решение в этом заезде уже было», станция, в радиусе которой стоит машина, и момент входа в радиус, флаги «стояла» и «обслужена», признак «в радиусе разгрузки» |
| Станция | кто занял и когда, момент последнего освобождения, последняя опубликованная очередь (одинаковые подряд не публикуются) |
| Рядом со снимком | офсеты входного топика |

Очереди не хранятся. Они пересчитываются из состояния машин на каждом сообщении: 40 машин × 4 станции, это микросекунды.

## 3. Телеметрия по машинам, очередь по станции, рекомендация по всем станциям

Разделения нет: один процессор держит и машины, и станции, поэтому менять ключ (машина → станция → площадка) не нужно. Нет перепартиционирования, промежуточных топиков и согласования между ними. Ключ — площадка.

Цепочка «процессор по `unit_uuid` → процессор по `station_uuid` → процессор решений» потребовала бы передавать «сейчас» и позиции машин через промежуточные топики. Пример задания показывает, что решение и очереди связаны в пределах одного сообщения:
- решение для T4 в 12:00:00 должно видеть очередь S1, уже посчитанную по сообщениям T1–T3 за ту же секунду;
- после решения T4 сразу уходит из очереди S1 в очередь S2.

С промежуточными топиками остаются два варианта: гонки (решение по устаревшим очередям) или барьеры по времени события, то есть та же глобальная синхронизация, только распределённая.

Нагрузка: 40 машин × 1 сообщение/с = 40 сообщений/с. Процессор на Python обрабатывает около 28 тыс. сообщений/с через Kafka (замер), запас примерно 700×.

## 4. Партиции, реплики, параллелизм

| Топик | Партиций | Почему |
|---|---|---|
| `telemetry.v1` | 1 | «Сейчас» — наибольший `ts` по всем машинам. От порядка сообщений разных машин зависят и «сейчас», и устаревание позиций, и то, какое опоздавшее сообщение будет отброшено. Порядок есть только внутри партиции. При нескольких партициях результат зависел бы от того, как консьюмер их перемежает, и повторный прогон давал бы другой ответ. |
| `queue.v1` | 1, compacted | Сжатие оставляет последнюю очередь каждой станции. Партиции по `station_uuid` можно добавить, порядок внутри станции сохранится. |
| `decision.v1` | 1 | Партиции по `unit_uuid` можно добавить. |
| `vq.state.v1` | 1, compacted | Один ключ на площадку. |

Реплики процессора: на площадку работает один экземпляр, потому что входная партиция одна. Второй экземпляр той же группы не добавляет пропускной способности. Отказоустойчивость дают перезапуск и восстановление меньше чем за секунду (п. 6). Топики создаются с фактором репликации брокера по умолчанию (`replication_factor=-1`).

Параллелизм ограничен числом площадок. Каждая площадка независима, у неё своё «сейчас», так что масштабирование идёт по площадкам: свой входной поток и свой экземпляр с отдельными `transactional.id` и `state_key`.

## 5. Гарантии доставки

**Транзакционность — на выходе сервиса.** Выход зависит от состояния: рекомендация выдаётся один раз за заезд, очередь публикуется только при изменении. Поэтому одна транзакция включает:
- выходы пачки входных сообщений (до 500 сообщений или 100 мс);
- снимок ядра в `vq.state.v1`;
- офсеты входа (`send_offsets_to_transaction`).

Читатель с `read_committed` видит либо всё, либо ничего: exactly-once.

**Идемпотентности достаточно на входе.** Генератор пишет с `enable.idempotence` и `acks=all`, поэтому ретраи продюсера не создают дублей в партиции. Дубли телеметрии, которые генератор создаёт сам (они есть по условию задачи), отсекает правило «`ts` не больше последнего учтённого — игнорировать».

**Читатели без `read_committed`.** Они могут увидеть выходы прерванных транзакций.
- Для решений есть заголовок `decision-id = {unit_uuid}:{ts сообщения-триггера}`. Он одинаков при повторном расчёте, по нему можно отбросить дубль.
- `queue.v1` — полное состояние очереди станции, так что повтор безвреден.

Задержка от отправки телеметрии до видимого выхода в реальном темпе: p50 184 мс, p90 234 мс.

## 6. Рестарт

**Откуда состояние.** Из последнего снимка в `vq.state.v1`. В том же снимке лежат офсеты входа, и консьюмер встаёт на них. Снимок и офсеты записаны одной транзакцией, поэтому всегда согласованы. Снимок несовместимой версии сервис не принимает и не стартует.

**Сколько времени** (замеры, от старта процесса до первого коммита):

| Случай | Время |
|---|---|
| Падение между транзакциями | 0,24 с |
| Падение посреди транзакции | 0,75 с |
| Чистый старт | 0,34–0,57 с |

- Чтение снимка занимает около 50 мс.
- Падение посреди транзакции дольше, потому что брокер сначала отменяет транзакцию убитого экземпляра.
- Заново обрабатывается только хвост после последнего коммита: до 500 сообщений, до 100 мс.
- Перезапущенный экземпляр сразу получает партицию обратно (`group.instance.id`) и отсекает своего зомби по эпохе продюсера.

**Что будет с уже выданными решениями.**
- **Рестарт со снимком.** Хвост после последнего коммита обрабатывается повторно. Выходы прерванной транзакции читатели `read_committed` не видят. Ядро детерминировано (время событий, без часов и случайности), поэтому повторный расчёт даёт те же решения с тем же `decision-id`. В e2e-тесте было три `kill -9` посреди транзакций за прогон: итог байт в байт совпал с офлайн-эталоном, без дублей и пропусков.
- **Проигрывание топика с начала с пустым состоянием** (новый `state_key`). Сервис выдаст все решения заново, с теми же значениями и теми же `decision-id`. Потребитель распознает их как повторы по заголовку. Генератор в замкнутом контуре применяет решение, только если машина едет к своей станции и в этом заезде ещё не перенаправлялась; решения с `at` раньше старта прогона он отбрасывает.

## 7. Что сознательно не вынесено в отдельный процессор

- **Состояние машин** (фаза, вход в радиус, «стояла», «обслужена») — не отдельный процессор по `unit_uuid`. Результат нужен очередям и решению в том же сообщении, а «сейчас» общее для площадки.
- **Очереди станций** — не отдельный процессор по `station_uuid`. Решение читает очереди всех станций, а переход машины из своей очереди в чужую — одно атомарное изменение.
- **Решения** — не процессор, читающий `queue.v1`. Опубликованная очередь — производное, а решению нужны позиция машины и очереди на момент того же сообщения. Через топик появились бы задержка и рассинхрон.
- **Дедупликация и порядок входа** — не отдельный этап. Это одно правило ядра, и оно зависит от состояния машины.
- **Теневой режим и метрика выигрыша** — параметры конфигурации, а не отдельные процессоры.

Ядро и Kafka разделены по модулям, но работают в одном процессе. Поэтому ядро тестируется без брокера, а запись прогона можно обработать офлайн (`vqservice process`) с тем же результатом, что и через Kafka.

# Виртуальные очереди

Сервис `vq-service` читает `telemetry.v1` из Kafka, восстанавливает очереди к станциям и публикует `queue.v1` и `decision.v1`. Генератор `vq-generator` симулирует площадку и пишет телеметрию в Kafka. Как разделена обработка — в [ARCHITECTURE.md](ARCHITECTURE.md).

```
site.yaml                общая площадка: 4 станции, точка разгрузки, 40 машин (seed 42)
service/                 сервис: vqservice/engine.py — правила, kafka_app.py — Kafka, service.yaml — конфигурация
gen/                     генератор: generator/, scenarios/task_example.yaml — пример из задания
Makefile                 kafka-up / kafka-down / test / test-kafka / demo
```

## Запуск

Нужны Python 3.12+ и Java 17+ (для локальной Kafka без Docker).

```bash
# окружения
(cd gen && python3.12 -m venv .venv && .venv/bin/pip install -e '.[test]')
(cd service && python3.12 -m venv .venv && .venv/bin/pip install -e '.[test]' -e ../gen)

# Kafka 3.9.1 (KRaft) на localhost:9092: скачивается один раз, данные удаляются при остановке
make kafka-up

# сервис: топики создаёт сам, состояние восстанавливает из vq.state.v1
cd service && .venv/bin/python -m vqservice run --config service.yaml
#   --shadow                 решения публикуются, но очереди их не учитывают
#   --metric service_end     выигрыш по моменту окончания обслуживания вместо ожидания

# генератор (в другом терминале)
cd gen && .venv/bin/python -m generator run --site ../site.yaml --speed 1                     # реальный темп
cd gen && .venv/bin/python -m generator run --site ../site.yaml --speed 10 --follow-decisions  # замкнутый контур
cd gen && .venv/bin/python -m generator run --scenario scenarios/task_example.yaml --no-faults --speed 1

make kafka-down
```

Без брокера тот же расчёт делается по записи прогона: `make demo` (1 ч генератора → `vqservice process` → `/tmp/vq-demo/out.jsonl`).

Остальные параметры: `python -m vqservice --help`, `python -m generator run --help`.

## Тесты

```bash
make test                          # оба набора, без брокера (тесты Kafka пропускаются)
make kafka-up && make test-kafka   # e2e на Kafka, с замерами; потом make kafka-down
```

Правила расчёта проверяются без брокера (`service/tests/test_engine_*.py`):

- занятие и освобождение станции;
- очередь;
- выбор станции;
- порядок и дубли;
- холодный старт;
- снимок и восстановление.

Пример из задания прогоняется через симулятор генератора (`test_engine_scenario.py`).

Интеграционные тесты:

- `make test`: офлайн-конвейер на часовой записи и замкнутый контур генератор ↔ ядро;
- `make test-kafka`: падение `kill -9` посреди транзакции и сравнение выхода с офлайн-эталоном.

## Что сделано

**Сервис** — один процессор на площадку. Он читает `telemetry.v1` с одной партицией, состояние всей площадки держит в памяти.

- `Engine` — чистые правила: время событий, без системных часов и случайности. Поэтому запись прогона даёт тот же результат через Kafka, офлайн и с ускорением.

- Exactly-once. Одна транзакция Kafka включает выходы пачки, снимок состояния в compacted `vq.state.v1` и офсеты входа. Рестарт восстанавливает состояние из снимка.

- У каждого решения есть заголовок `decision-id = {unit_uuid}:{ts сообщения-триггера}`: при повторном расчёте он тот же.

- Теневой режим (`--shadow`): решения публикуются, очереди их не учитывают.

- Две метрики выигрыша:

  | Метрика                     | Что сравнивает                                           |
  | --------------------------- | -------------------------------------------------------- |
  | `queue_wait` (по умолчанию) | ожидание, как в правилах задания                         |
  | `service_end`               | момент окончания обслуживания: дорога + ожидание + 230 с |

**Генератор.**

- Машины ездят по прямой со скоростью 10 м/с. Такт 1 с, все машины в одной секунде, внутри такта — по `unit_uuid`.

- Координаты по умолчанию с 4 знаками, как в примере телеметрии из задания; `--coord-precision 6` для точных проверок.

- Очередь у станции — по входу в радиус 50 м. Обслуживание 200 с. Остановка в 15 м до центра станции.

- Манёвр между машинами по умолчанию 0, `--maneuver-seconds 30` совпадает с моделью сервиса (230 с).

- Помехи (все случайности — от seed, опоздание не больше 60 с):

  | Помеха                    | Частота и размер                                         |
  | ------------------------- | -------------------------------------------------------- |
  | Дубли                     | 1 % записей                                              |
  | Задержка отдельной записи | 2 % записей, 1–60 с                                      |
  | Потеря связи у машины     | ~2 раза в час, 10–60 с, накопленный хвост приходит разом |

  В сценарии можно задать опоздание конкретных записей (поле `delays`).

- Режимы:

  - открытый контур или `--follow-decisions` (генератор выполняет рекомендации);
  - запись прогона и `replay`;
  - эталон физических событий (`--truth`) для сверки прогноза с фактом.

**Пример из задания** (`gen/scenarios/task_example.yaml`) воспроизведён с числами задания.

- Записи T4 за 11:59:01–11:59:59 приходят в 12:00:01, после её записи 12:00:00. Первая учтённая запись T4 ближе 1500 м — в 900 м.
- В 12:00:00 позиция T4 старше 30 с, поэтому очередь S1 — T1/T2/T3 с ожиданием 0/50/100 с.
- Решение для T4: `recommended` S2, выигрыш 80 с. С метрикой `service_end` — `no_gain`: S1 закончит обслуживание в 12:06:40, S2 в 12:07:50.
- Расчёт расписан в комментариях YAML.

**Замеры** (локальный брокер, один экземпляр):

| Что                                             | Значение                                           |
| ----------------------------------------------- | -------------------------------------------------- |
| Пропускная способность через Kafka              | ~28 тыс. сообщений/с; площадка даёт 40 сообщений/с |
| Задержка от телеметрии до выхода, реальный темп | p50 184 мс, p90 234 мс                             |
| Снимок состояния                                | ~10 КБ                                             |
| Восстановление после `kill -9`                  | 0,24–0,75 с                                        |
| `queue.v1`                                      | ~41–46 тыс. сообщений в час                        |
| `decision.v1`                                   | ~70 в час                                          |

### Как применены правила там, где данных недостаточно

- **Расстояние** — по формуле гаверсинуса, сфера R = 6371 км.
- **ETA** — от момента позиции: `ts + расстояние / 10 м/с`, округление до секунды (половина вверх), не раньше «сейчас».
- **Порядок занятия.** Правила применяются во времени событий. Если опоздавшее сообщение показывает, что машина стояла в радиусе, пока станция была свободна, она заняла станцию в этот момент. Тогда та, что заняла станцию по более позднему сообщению, ждёт. Ничью внутри одной секунды правило не разрешает: её решает порядок приезда (вход в радиус), затем `unit_uuid`.
- **Станции на холодном старте.** По телеметрии не видно, кто из стоящих в радиусе машин обслуживается, когда сервис стартует на идущем потоке.
  - Сервис считает занявшей первую по входу в радиус, при равенстве — по `unit_uuid`.
  - Если из радиуса уезжает другая машина, которая там стояла, значит, обслуживали её. Её заезд заканчивается («к разгрузке»), а занятие, выбранное сервисом, отменяется: станция свободна с этого момента.
- **Рекомендации на холодном старте** — по правилу: первое сообщение заезда ближе 1500 м в состоянии «к станции», включая первое сообщение машины. Поэтому решение получают и машины, которые на самом деле едут к разгрузке.
  - В замкнутом контуре генератор такие рекомендации не выполняет.
  - Сервис учитывает машину в очереди рекомендованной станции, пока она не займёт станцию или не закончится её заезд.
  - Машина, чьё первое сообщение «на станции», в этом заезде решения не получает.
- **Освобождение таймером.** Машина, которую освободил таймер 230 с, но которая ещё стоит в радиусе, станцию снова не занимает.

## Что сознательно не сделано

- **Несколько партиций и экземпляров на площадку.** «Сейчас» — наибольший `ts` по всем машинам, и от порядка их сообщений зависят и устаревание позиций, и отброс опоздавших. Детерминированный результат даёт только одна партиция. Масштабирование — по площадкам: у каждой своё «сейчас», свой входной поток и свой экземпляр.
- **Горячий резерв.** Второй экземпляр не добавляет пропускной способности. Перезапуск со снимком занимает меньше секунды.
- **Подавление мелких изменений `queue.v1`.** Правило требует публиковать любое изменение времени в очереди. Около 95 % публикаций — сдвиг ETA на 1–2 с из-за 4 знаков в координатах генератора; с `--coord-precision 6` их около 4,5 тыс. в час вместо ~44 тыс.
- **Docker и Schema Registry.** Kafka запускается скриптом (`gen/scripts/kafka_local.sh`, нужна только Java). Сообщения — JSON в формате задания.
- **Метрики для мониторинга.** Сервис раз в 10 с пишет сводку в stderr: прочитано, отставание, коммиты, «сейчас», счётчики ядра.
- **Коммит сразу после неполной пачки.** Он сократил бы задержку примерно вдвое. Сейчас транзакция фиксируется раз в 100 мс или каждые 500 сообщений; при 40 сообщениях/с этого достаточно.
